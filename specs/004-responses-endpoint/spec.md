# Feature Specification: Responses Endpoint End to End

**Feature Branch**: `004-responses-endpoint`

**Created**: 2026-10-10

**Status**: Draft

**Input**: User description: "Ok, now that we have a proper first endpoint, analytics and tracability, let's implement the second endpoint: responses. We should follow the same pattern for implementation, have the response table to record the same proper metadata as we do for chat, support the analytics and tracability for the endpoint, and for the Playground, we can have a brand new window for the responses endpoint, also in the left sidbar, we can have sub buttons (one for chat one for responses) for better navigation."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Create a response through the OpenAI-compatible endpoint (Priority: P1)

A developer points an existing OpenAI SDK client at the local server (changing only the base URL) and creates a response with the Responses API, using either a plain text input or a structured list of input items, optionally with instructions. They receive a response generated by the local model, in the exact shape OpenAI clients expect, either as a single response object or as a stream of typed events. Every generation request that reaches the endpoint logic, successful or failed, is recorded with its metadata so it can be analysed later, in the same way chat completions are.

**Why this priority**: This is the core of the feature: a drop-in, fully local replacement for OpenAI's Responses endpoint. Every other story depends on it.

**Independent Test**: With the server and local model running, create a response using an unmodified OpenAI SDK (non-streaming, then streaming). Verify a valid response comes back and that a metadata record of the request exists afterwards.

**Acceptance Scenarios**:

1. **Given** the server is running with the local model available, **When** a client creates a response from a text input, **Then** it receives a complete response object containing the model's output, a status, and token usage, matching OpenAI's response shape.
2. **Given** the same setup, **When** the client sends a list of input items (messages with roles, text and inline images) together with instructions, **Then** the instructions and items are all taken into account by the model and the response is returned in the same shape.
3. **Given** the same setup, **When** the client requests streaming, **Then** it receives OpenAI's typed stream events in order (created, in progress, output item and content deltas, completed), and the final usage figures are present in the terminal event.
4. **Given** a request that uses any option defined by OpenAI for this endpoint (sampling controls, maximum output tokens, text format including structured output, tools and tool choice, reasoning, truncation, metadata, and so on), **When** it is sent, **Then** the request is accepted and each option is either honored by the local model or handled according to a documented policy (honored, accepted and ignored, or rejected as unsupported) for options a local model or this server cannot honor.
5. **Given** a malformed or invalid request (missing input, wrong types, out-of-range values), **When** it is sent, **Then** the client receives an OpenAI-style error that the SDK maps to the right exception type; the request is not recorded, since no generation was attempted. A well-formed request that fails afterwards (unsupported option, model not served, upstream failure) is recorded as failed.
6. **Given** a request naming a model the server does not serve (e.g. `gpt-4o`), **When** it is sent, **Then** the client receives the same `model_not_found` error OpenAI returns for an unknown model, and the failed request is recorded.
7. **Given** the local model runtime is unreachable, **When** a request is sent (streaming or not), **Then** the client receives a clear OpenAI-style server error with a proper HTTP status instead of a hang or crash, and the failure is recorded.
8. **Given** a client disconnects mid-stream, **When** the disconnection occurs, **Then** generation stops and the request is recorded as cancelled with whatever usage is known.

### User Story 2 - Responses playground in the web app (Priority: P2)

A user opens the web app and finds, in the left sidebar, a "Playground" entry that groups two sub-entries: "Chat" and "Responses". Selecting "Responses" opens a dedicated window for the Responses endpoint: they enter an input and optional instructions, adjust every option the endpoint offers through form controls, send the request, and read the model's answer (live as it streams, or all at once). The window shows a history of the requests sent from it, each as just a request and its answer.

**Why this priority**: It makes the endpoint testable without writing code and mirrors what the chat playground already offers. It depends on Story 1 but is independently demonstrable once the endpoint exists.

**Independent Test**: Open the Responses playground, send a message with streaming on and then off, and confirm the answer is displayed and the history lists both exchanges.

**Acceptance Scenarios**:

1. **Given** the app is open, **When** I look at the sidebar, **Then** I see "Playground" with the sub-entries "Chat" and "Responses", and the entry for the page I am on is highlighted.
2. **Given** I select "Chat", **When** the page loads, **Then** it is the existing chat playground, unchanged in behavior, at its new conventional address.
3. **Given** I select "Responses", **When** the page loads, **Then** I see an input area, an instructions field, a model selector, and controls for the options of the endpoint, separate from the chat playground.
4. **Given** I send a request with streaming on, **When** the model generates, **Then** the answer appears progressively and I can stop it; with streaming off, the full answer appears when done.
5. **Given** a request fails (unknown model, unreachable runtime, unsupported option), **When** the error returns, **Then** the playground shows the server's error message as-is in that history entry.
6. **Given** I have sent several requests, **When** I view the history, **Then** each entry shows its request and answer (or error), and the history is scoped to the Responses playground (chat history is not mixed in).

### User Story 3 - Responses in the Analytics tab (Priority: P2)

A user opens the Analytics tab and sees one table containing every recorded generation request, from all endpoints (chat completions and Responses), newest first: time of request, endpoint, model, status, streaming flag, token counts (input, output, total), timing (total duration, time to first token, generation duration), and error type, but never the request or response text. Above the table, the same filter the Observability tab offers (endpoint, date range) plus a status filter lets the user narrow the table and its summary figures to, for example, only failed Responses requests since yesterday.

**Why this priority**: The user explicitly asked for analytics support for the new endpoint, but it needs recorded data (Story 1) to be meaningful.

**Independent Test**: Send successful, failed and streamed requests to both endpoints, open the Analytics tab, and confirm all appear in one table with correct token counts and timings and no content visible; then apply endpoint, date and status filters and confirm the table and summary follow.

**Acceptance Scenarios**:

1. **Given** requests have been made to both endpoints, **When** I open the Analytics tab, **Then** I see one table with one row per request, newest first, in pages, each row naming its endpoint, with no content.
2. **Given** the same data, **When** I look at the summary figures, **Then** they cover the same requests as the table (counts, error count, total tokens, average durations).
3. **Given** I pick an endpoint in the filter, **When** the data reloads, **Then** the table and summary show only that endpoint's requests.
4. **Given** I pick a status (succeeded, failed, cancelled) or a date range, **When** the data reloads, **Then** the table and summary show only matching requests; combining filters narrows further.
5. **Given** a request that failed or was cancelled, **When** I view it in Analytics, **Then** its status and error type are shown and token counts are shown only where known.
6. **Given** no request matches the filters, **When** the table loads, **Then** an empty state says so and offers to clear the filters.

### User Story 4 - Responses in the Observability tab (Priority: P2)

A user opens the Observability tab and sees Responses requests in the live feed next to chat requests, can filter the feed by the Responses endpoint, and can open any Responses request to follow its workflow step by step: request received, request sent to Ollama, response received from Ollama (assembled in full for streams), response returned, plus errors. In-progress, failed, cancelled and interrupted requests are handled exactly as for chat.

**Why this priority**: The user asked for traceability on the new endpoint; the tracing mechanism already exists and must be extended to recognise this endpoint.

**Independent Test**: Send a streaming Responses request, watch it appear in the feed as in progress, then open its detail and confirm the sequence shows the incoming request, the outgoing Ollama payload, the assembled Ollama result, and the final response, with timings.

**Acceptance Scenarios**:

1. **Given** the Observability tab is open, **When** a Responses request is made, **Then** a new feed entry appears showing the Responses endpoint and an in-progress state, then updates in place with its final outcome and duration.
2. **Given** the feed holds chat and Responses requests, **When** I filter by the Responses endpoint, **Then** only those are shown and new matching requests still arrive live.
3. **Given** a completed Responses request, **When** I select it, **Then** I see the sequence between client, API and Ollama with direction, time offsets, durations, and expandable full content for each step.
4. **Given** a Responses request that failed before or at Ollama, or was cancelled mid-stream, **When** I select it, **Then** the failing step is clearly highlighted with the error, and partial content received before a cancel is preserved.
5. **Given** a recorded Responses request, **When** I look at its detail, **Then** it is linked to its metadata record (the Analytics-side record) the same way chat requests are.

### Edge Cases

- A request that sets `store` (stored responses) or `previous_response_id` (conversation chaining): this server does not keep responses for later retrieval or chaining, so these fall under the documented option policy rather than silently misbehaving (see Assumptions).
- Retrieval, deletion, cancellation and input-item listing of a stored response (`GET`/`DELETE`/`POST cancel`/`GET input_items` on a response id) are not implemented and return the standard unknown-route/method error.
- Built-in OpenAI hosted tools (web search, file search, code interpreter, computer use, and so on) cannot run locally and are handled per the option policy; custom function tools are supported to the extent the local model supports them.
- Input items of types the local model cannot consume (audio, files, hosted-tool outputs) are rejected as unsupported rather than dropped silently.
- Empty or very long input is passed through; only the model context limit applies, subject to the `truncation` option's documented policy.
- A structured-output request whose generated text does not conform to the requested schema is returned as generated (no server-side validation or retry), as with chat.
- A client disconnecting before the first event is recorded as cancelled with unknown token counts.
- The Playground sub-navigation must remain usable when the sidebar is collapsed or on a narrow window.
- The former single `/playground` address no longer exists; navigation uses the new Chat and Responses addresses only.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST expose the OpenAI "create a model response" operation (`POST /v1/responses`) with request and response shapes matching OpenAI's published contract for success and error cases, for both non-streaming and streaming modes, so unmodified OpenAI SDK clients work by changing only the base URL.
- **FR-002**: The system MUST accept every property OpenAI defines on the create-response request and handle each according to a documented policy (honored, accepted and ignored, or rejected as unsupported). A test MUST assert the policy covers every property of the vendored request schema.
- **FR-003**: The system MUST accept input as a plain string or as a list of input items (messages with roles, text, and inline images), and MUST apply `instructions` as the leading system guidance for the model.
- **FR-004**: In streaming mode the system MUST emit OpenAI's typed response stream events in the correct order and with the correct payloads, ending the stream the way OpenAI's does; token usage MUST be present in the terminal event.
- **FR-005**: The system MUST serve only models known to the server, reject any other model name with the same `model_not_found` error OpenAI returns, and fail clearly (OpenAI-style error, proper status) when the local runtime is unreachable.
- **FR-006**: The system MUST record, for every request that reaches the endpoint logic (success, failure, or cancellation), a metadata record with the same categories of information as chat completion records: external response id, creation time, model, status (succeeded, failed, cancelled), streaming flag, input and output token counts, total duration, time to first token, generation duration, model load duration, finish information, and error type and code.
- **FR-007**: The system MUST store the request content and response content of each recorded request separately from the metadata, so metadata can be exposed without content.
- **FR-008**: Requests rejected by schema validation before reaching generation logic MUST NOT be recorded as metadata records; well-formed requests that fail later (unsupported option, unknown model, upstream failure) MUST be recorded as failed.
- **FR-009**: The Analytics tab MUST show the requests of all endpoints (chat completions and Responses) in a single content-free metadata table, paged, newest first, each row identifying its endpoint, with summary figures computed over the same set of requests. Request and response text MUST never be present in what Analytics receives or displays.
- **FR-009a**: The Analytics tab MUST offer filters by endpoint, date range, and status (succeeded, failed, cancelled), reusing the same filter component and behavior as the Observability tab; the table and summary figures MUST both honor the active filters.
- **FR-010**: The system MUST expose analytics through additional (non-OpenAI) `/v1` endpoints serving the combined, filterable table and summary; these replace the existing chat-only analytics endpoints (no backward compatibility is required).
- **FR-011**: The Responses endpoint MUST be a tracked endpoint for API-point-of-view observability: every request to it is recorded with its workflow steps (request received, request sent to Ollama, response received from Ollama with streams assembled in full, response returned, error), linked to its metadata record, with the same outcome, streaming, cancellation and interruption semantics as chat completions. Individual stream events MUST NOT be stored as separate steps.
- **FR-012**: The Observability tab MUST display Responses requests in its live feed, support filtering by the Responses endpoint, and render the Responses workflow detail with the same sequence view and expandable content as chat.
- **FR-013**: The web app sidebar MUST present "Playground" as a group with two sub-entries, "Chat" and "Responses", highlight the active one, and keep Analytics and Observability reachable as before.
- **FR-014**: The web app MUST provide a Responses playground page, separate from the chat playground, with form controls for the options the server honors or accepts (per FR-002), and a raw JSON field through which any other option can still be sent so the server's response to it is displayed as-is, a model selector, input and instructions fields, a streaming on/off switch with cancellation, and a session-scoped history of request/answer pairs showing server errors as-is.
- **FR-015**: Resource ids for responses MUST follow OpenAI's prefixed id format for responses.
- **FR-016**: Behavior of the existing chat completions endpoint and chat playground MUST be unchanged by this feature; chat analytics is superseded by the combined Analytics view (FR-009).

### Key Entities *(include if feature involves data)*

- **Response Record**: The metadata of one generation request to the Responses endpoint, the counterpart of the chat completion record: external id, creation time, model, status, streaming flag, token counts (input, output, total), timing (total duration, time to first token, generation duration, load duration), finish information, error type and code. Never contains request or response text.
- **Response Content**: The stored request and response payloads and error message for one Response Record, kept apart from the metadata as the durable record of what was sent and returned. Nothing reads it yet (Observability detail is built from workflow steps); it is never exposed to Analytics.
- **Traced Request / Workflow Step** (existing): Extended to recognise the Responses endpoint, linking each traced Responses request to its Response Record.
- **Playground History Entry**: A user-facing pairing of a request (input, instructions, options) with its answer or error, as seen in the Responses playground; kept in the browser for the session.
- **Model** (existing): The served local model(s), reused unchanged for validation and the playground selector.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: An unmodified OpenAI SDK client, with only its base URL changed, completes both a non-streaming and a streaming Responses request successfully against the server.
- **SC-002**: 100% of the options defined by OpenAI for this endpoint pass schema validation when well-formed, each documented as honored, ignored, or rejected, with a test asserting the policy table covers every property of the vendored request schema.
- **SC-003**: Responses from the server (including error responses and every stream event) pass automated validation against OpenAI's published contract.
- **SC-004**: For streaming requests, the first content appears in the Responses playground within 2 seconds of sending once the model is loaded, on the target platform (a macOS Apple-silicon machine).
- **SC-005**: 100% of generation requests to either endpoint that reach the endpoint logic (success, failure, cancelled) appear in the Analytics tab, with token counts matching those returned to the client, and every filter combination returns exactly the matching requests.
- **SC-006**: No request or response text is ever present in what the Analytics tab receives or displays for Responses requests.
- **SC-007**: 100% of Responses requests appear in the Observability feed, including failed and cancelled ones, and a new request appears in an open Observability tab within 1 second of the server receiving it.
- **SC-008**: A user can reach either playground (Chat or Responses) from the sidebar in one click, and can send a first Responses message and read the answer in under 1 minute from opening the app, with no further configuration.
- **SC-009**: Chat completions endpoint behavior is unchanged: the existing chat endpoint test suites continue to pass without modification of their expectations (Analytics and filter tests are updated for the combined view).
- **SC-010**: The Analytics and Observability tabs stay responsive (list visible in under 2 seconds) with at least 10,000 recorded requests across both endpoints.

## Assumptions

- Single local user, no authentication, consistent with current conventions; Playground, Analytics and Observability show all requests regardless of origin.
- Only the create operation is in scope. The stored-response operations of OpenAI's Responses API (retrieve, delete, cancel, list input items, input token counting, compaction) are not implemented and return the standard unknown-route/method error. Consequently the server is stateless for conversation purposes: `store` and `previous_response_id` are covered by the option policy (the policy is decided in planning; the default is that `store` is accepted and ignored since nothing is retrievable, and `previous_response_id` is rejected as unsupported so a client never silently loses context).
- The model, Ollama access, and model validation are reused from the chat feature; no new model is introduced.
- Hosted tools (web search, file search, code interpreter, computer use, MCP connectors) cannot run locally and fall under the "rejected as unsupported" policy; custom function tools are honored where the local model supports tool calling. The exact per-option policy table is produced during planning.
- Audio input and file input items are unsupported; text and inline (base64) image content are supported, as for chat.
- Reasoning options are honored only where the local model has an equivalent; otherwise they are accepted and ignored.
- Metadata for Responses is stored in its own dedicated tables (metadata and content), following the chat completion record pattern. The chat and Responses tables are deliberately NOT merged or unified.
- No backward compatibility is required at this stage: this is a single-developer local tool with no other users, so existing schema, data, and addresses may be dropped, recreated, or renamed freely when that gives a cleaner result.
- Analytics presents one blended table of all endpoints (decided with the user during planning), with filters rather than a per-endpoint switch.
- The Playground history shows only requests made from that playground and lives in the browser for the session; the durable history is the stored records.
- Playground navigation uses conventional, hierarchical addresses (a Playground section with `chat` and `responses` pages); the old flat `/playground` address is removed rather than redirected, and the app's root opens the chat playground.
- Observability data and history follow spec 003's rules (kept in full, milestone-level real time, restart-safe, tracking never breaks the request).
- Constitution compliance: local-only inference through Ollama (Principle II) is honored; the endpoint matches the OpenAI contract exactly (Principle I) and additional analytics endpoints live under `/v1` without shadowing any OpenAI path; usage and request state live in SQLite and feed the UI through `/v1` endpoints (Principle V), with this endpoint explicitly decided as tracked and supported by the Observability UI; live-request priority (Principle IV) is trivially satisfied as no batch workload exists yet.
