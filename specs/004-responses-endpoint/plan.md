# Implementation Plan: Responses Endpoint End to End

**Branch**: `004-responses-endpoint` | **Date**: 2026-10-10 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `/specs/004-responses-endpoint/spec.md`

## Summary

Add OpenAI's `POST /v1/responses` (create only, streaming and non-streaming) on top of the
existing Ollama `/api/chat` client, translating Responses requests/outputs/stream events
ourselves. Like chat, every request that reaches the endpoint logic is recorded once in its own
tables (`response_records` metadata + `response_contents` payloads; deliberately not merged with
the chat tables) and traced by the existing observability mechanism (the endpoint is added to the
tracked set). The endpoint-agnostic machinery in `chat/service.py` (error mapping, totals, race
against client disconnect, shielded recording, trace helpers, think levels, field-policy enum) is
extracted into a shared `api/inference.py` because a second consumer now exists. Analytics becomes
**one combined, filterable table** over both record tables (endpoint, date range, status), served
by new `/v1/analytics/requests` endpoints that replace the chat-only analytics endpoints.
The web app gets a "Playground" sidebar group (Chat, Responses) with conventional nested routes
(`/playground/chat`, `/playground/responses`), a Responses playground page, a shared request
filter component used by Analytics and Observability, and Responses support in both tabs.
No backward compatibility is kept anywhere (spec Assumptions).

## Technical Context

**Language/Version**: Python ≥ 3.14 (backend); TypeScript strict, React 19 (frontend)

**Primary Dependencies**: none new. FastAPI, Pydantic, SQLAlchemy async + Alembic, httpx (existing
`llm` package, unchanged); frontend: existing TanStack Query, React Router, shadcn/ui (the
`sidebar` sub-menu primitives already exist in `components/ui/sidebar.tsx`)

**Storage**: SQLite via `packages/db`; two new tables (`response_records`, `response_contents`),
one Alembic migration (autogenerated, then reviewed). The `chat_completion_*` tables are unchanged
on disk (only the Python status enum is renamed to a shared `RequestStatus`, see research R9)

**Testing**: pytest + pytest-asyncio + httpx ASGI transport, Ollama mocked via the existing
`OllamaMock`; `validate_contract` for non-stream success/error, `validate_schema(…,
"ResponseStreamEvent")` for every streamed event, policy-table coverage test over the vendored
`CreateResponse` schema; repository tests on in-memory SQLite; one `@pytest.mark.integration` SDK
test; Vitest + Testing Library + MSW for the frontend

**Target Platform**: single local macOS Apple-silicon machine, Ollama on localhost

**Project Type**: web application (FastAPI backend + Vite SPA) in a uv/pnpm monorepo

**Performance Goals**: first streamed content in the Responses playground ≤ 2 s once the model is
loaded (SC-004); new request visible in an open Observability tab ≤ 1 s (SC-007); combined
Analytics list ≤ 2 s at ≥ 10,000 records across both tables (SC-010)

**Constraints**: handlers `async def`; no DB statements outside `packages/db`; recording failures
never fail the request; `mypy --strict`; no `any` in TS; OpenAI wire contract exact (so a Responses
stream has **no** `[DONE]` sentinel and carries `event:` lines, see research R6); no backward
compatibility needed

**Scale/Scope**: single user; 1 new OpenAI endpoint, 2 new non-OpenAI analytics endpoints
(replacing 2), 1 new tracked endpoint, 1 new frontend page + reworked Analytics/sidebar/filters

## Constitution Check

*GATE: pass before Phase 0; re-checked after Phase 1.*

| Principle | Status | Notes |
|---|---|---|
| I. OpenAI-compatible surface | Pass | `POST /v1/responses` follows the vendored contract exactly (validated per response and per stream event). Only create is implemented; other `/v1/responses/*` operations return the standard unknown-route/method error, not a different contract. Analytics lives under `/v1/analytics/requests`, which shadows no OpenAI path. The stream wire format follows OpenAI's Responses format rather than chat's (no `[DONE]`): this is contract fidelity; the CLAUDE.md "Streaming" convention was amended accordingly during planning. |
| II. Fully local | Pass | Same Ollama-only client; no new network calls. |
| III. Lightweight, minimal deps | Pass | No new dependency or service. Schema change ships with its Alembic migration. |
| IV. Live priority over batch | Pass (N/A) | No batch workload exists. |
| V. State & observability via SQLite | Pass | Per-request usage recorded in `response_records`; API-point-of-view tracing added by extending the tracked set (decision recorded: **tracked**, and the Observability tab supports it). Analytics reads the DB through `/v1` only. |

Project conventions: YAGNI honored: no generated schemas, no generic repository base class (the
combined analytics query is one read-only module, `db/repositories/analytics.py`), no per-endpoint
`conftest.py`, no stored-response operations, no reasoning-output items. The only new abstraction
is `api/inference.py`, justified by the second concrete consumer (research R2). DB-only-in-db
honored (the shared module and services call repository functions only). Naming: Pydantic classes
use OpenAI's schema names verbatim; separate tables per the user's decision.

No violations → Complexity Tracking omitted. *Post-design re-check*: unchanged.
