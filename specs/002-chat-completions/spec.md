# Feature Specification: Chat Completions End to End

**Feature Branch**: `002-chat-completions`

**Created**: 2026-10-03

**Status**: Draft

**Input**: User description: "Let's have our first feature: the basic chat completion endpoint of openai. We want the feature from end to end; that is to say in the frontend, we should have two tabs (accessible from the side bar) first a tab where we can play with the endpoint, having a ui for all of the options that it proposes, and where we can send a request and get the llm response with the request history (just request/answer); then a second tab where we have the analysis of all the request, the time of request, the token count, the time of generation taken etc etc (but not the content). In the backend we should have the fully implemented endpoint with all the options of openapi so that we support properly the full endpoint. In the packages we should update the db to be able to store metadata of each request, input token, output token, input, output, etc etc. And in the llm package we should have the llm client needed for the calls, based for now on ollama. As for the local model we will use qwen model, the latest possible but under 10B tokens."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Chat completion through the OpenAI-compatible endpoint (Priority: P1)

A developer points an existing OpenAI SDK client at the local server (changing only the base URL) and sends a chat completion request. They receive a response generated by the local Qwen model, in the exact shape OpenAI clients expect, either as a single response or as a stream of chunks. Every generation request that reaches the endpoint logic, successful or failed, is recorded with its metadata so it can be analysed later.

**Why this priority**: This is the core value of the project: a drop-in, fully local replacement for the OpenAI chat completions endpoint. Without it, nothing else in this feature has data or purpose.

**Independent Test**: With the server and local model running, send a chat completion request using an unmodified OpenAI SDK (non-streaming, then streaming). Verify a valid response comes back and that a record of the request exists afterwards.

**Acceptance Scenarios**:

1. **Given** the server is running with the local model available, **When** a client sends a valid chat completion request with a list of messages, **Then** it receives a complete response containing the model's reply, a finish reason, and token usage, matching OpenAI's response shape.
2. **Given** the same setup, **When** the client requests streaming, **Then** it receives incremental chunks in OpenAI's streaming format, ending with the standard termination marker, and the final usage figures are available when the client asks for usage in the stream.
3. **Given** a request that uses any option defined by OpenAI for this endpoint (sampling controls, stop sequences, number of choices, token limits, response format, tools and tool choice, log probabilities, seed, and so on), **When** it is sent, **Then** the request is accepted and each option is either honored by the local model or handled according to the documented policy for options a local model cannot honor.
4. **Given** a malformed or invalid request (missing messages, wrong types, out-of-range values), **When** it is sent, **Then** the client receives an OpenAI-style error that the SDK maps to the right exception type; the request is not recorded, since no generation was attempted. A well-formed request that fails afterwards (unsupported option, model not served, upstream failure) is recorded as failed.
5. **Given** a request naming a model the server does not serve (e.g. `gpt-4o`), **When** it is sent, **Then** the client receives the same `model_not_found` error OpenAI returns for an unknown model, and the failed request is recorded.
6. **Given** the local model runtime is unreachable, **When** a request is sent (streaming or not), **Then** the client receives a clear OpenAI-style server error with a proper HTTP status instead of a hang or crash, and the failure is recorded.
7. **Given** a client disconnects mid-stream, **When** the disconnection occurs, **Then** generation stops and the request is recorded as cancelled or incomplete with whatever usage is known.

### User Story 2 - Playground tab to try the endpoint (Priority: P2)

A user opens the web app and selects the "Playground" tab from the sidebar. They compose a conversation, adjust every option the chat completions endpoint offers through form controls, send the request, and read the model's answer (live as it streams, or all at once). The tab shows a history of the requests sent in this tab, each as just a request and its answer.

**Why this priority**: It makes the endpoint usable and testable without writing code, and is the main way to exercise all options visually. It depends on Story 1 but is independently demonstrable once the endpoint exists.

**Independent Test**: Open the Playground, type a message, send it, and see the answer appear; change an option (e.g. temperature, streaming on/off), send again, and see both exchanges in the history.

**Acceptance Scenarios**:

1. **Given** the Playground is open, **When** the user writes a message and sends it, **Then** the model's answer is displayed and the exchange (request and answer) is added to the history.
2. **Given** streaming is enabled, **When** the user sends a request, **Then** the answer appears progressively and the user can cancel generation before it completes.
3. **Given** the options panel, **When** the user browses it, **Then** every option of the chat completions endpoint has a corresponding control, with sensible defaults, and options left untouched are not sent.
4. **Given** the server returns an error, **When** the request fails, **Then** the error message is shown to the user as-is and the failed attempt appears in the history.
5. **Given** the history contains earlier exchanges, **When** the user selects one, **Then** they can see the full request (messages and options) and its answer.

---

### User Story 3 - Analytics tab for request metadata (Priority: P3)

A user selects the "Analytics" tab from the sidebar and sees a view of every request ever made to the endpoint (from the Playground or any SDK client): when it was made, which model, whether it succeeded, input and output token counts, how long the request took, time to first token (streaming), model load time, how long generation took, and similar timing figures. The message content (inputs and outputs) is never shown here.

**Why this priority**: It provides observability and usage accounting. It is valuable but only meaningful once requests are flowing (Story 1) and benefits from the Playground for generating traffic (Story 2).

**Independent Test**: Make several requests (mixed success, failure, streaming and non-streaming), open the Analytics tab, and verify each appears with correct metadata and no message content.

**Acceptance Scenarios**:

1. **Given** requests have been made, **When** the user opens Analytics, **Then** a list shows each request with timestamp, model, status, input tokens, output tokens, total tokens, total duration, time to first token (where applicable), model load duration, and generation duration, newest first.
2. **Given** a large number of requests, **When** the user scrolls or pages, **Then** older requests load progressively without the view becoming unusable.
3. **Given** the list is shown, **When** the user inspects any row, **Then** no prompt or response text appears anywhere in the view.
4. **Given** no requests exist yet, **When** the user opens Analytics, **Then** an empty state explains that no requests have been recorded.
5. **Given** requests exist, **When** the user views Analytics, **Then** summary totals (request count, total tokens in and out, average durations) are shown above the list.

### Edge Cases

- A request has `n` greater than one: all choices are returned, and usage covers all of them.
- A request asks for streaming and multiple choices at once.
- A conversation exceeds the model's context window: the client receives an OpenAI-style context-length error, not a silent truncation.
- The requested model name is not a served model (including OpenAI model names like `gpt-4o` sent by SDK clients): rejected with OpenAI's `model_not_found` error.
- The request body contains fields the server does not know (newer SDK versions): they are tolerated, not rejected.
- Request asks for an option that depends on a capability the local model lacks (audio output, web search, image input on a text model).
- A tool-calling request where the model returns tool calls instead of text.
- A structured-output request (JSON mode or JSON schema) where the model's output does not conform.
- Streaming fails midway after chunks have already been sent.
- The model is not yet downloaded or still loading when the first request arrives.
- Very long or empty message content; messages with mixed text parts.
- Analytics requested while a streaming request is still in flight: that request shows as in progress or is omitted until it finishes, never with wrong figures.

## Requirements *(mandatory)*

### Functional Requirements

**Endpoint behavior**

- **FR-001**: The system MUST expose a chat completions endpoint at the same path and with the same request and response contract as OpenAI's, so that an unmodified OpenAI SDK works by changing only the base URL.
- **FR-002**: The system MUST accept every request field defined by OpenAI for this endpoint, and MUST tolerate unknown extra fields without rejecting the request.
- **FR-003**: The system MUST honor, with the local model, every option that has a meaningful local equivalent: messages of all roles (including text content parts and inline base64 image parts), sampling controls (temperature, top-p, seed), penalties, stop sequences, token limits, number of choices, response format (text, JSON mode, JSON schema), tools and tool choice, log probabilities, and streaming with its options.
- **FR-004**: For options that carry no meaning for local inference and do not change the generated output (e.g. service tier, cache hints, safety identifier, user identifier, metadata, store), the system MUST accept them without error and ignore them.
- **FR-005**: For options that request a capability the local model cannot provide (e.g. audio output, web search), or whose silent ignoring would change the generated output (e.g. a non-empty `logit_bias`, remote image URLs), the system MUST reject the request with an OpenAI-style invalid-request error naming the unsupported option, rather than silently returning a degraded result.
- **FR-006**: Non-streaming responses MUST include the generated choices, finish reasons, model name, creation time, a prefixed unique identifier, and token usage, in OpenAI's response shape.
- **FR-007**: Streaming responses MUST follow OpenAI's streaming format exactly, including the termination marker and optional final usage chunk.
- **FR-008**: Errors MUST use OpenAI's error envelope, with the status codes and error types OpenAI uses for the same conditions (invalid request, model not found, context length exceeded, server error).
- **FR-009**: Inference MUST be performed only by the local Ollama-served Qwen model; no request may be forwarded to any remote service.
- **FR-010**: The initially served model MUST be the most recent Qwen generation available through Ollama with fewer than 10 billion parameters. The set of served models is stored in the database (not hardcoded) and a request naming any other model MUST be rejected with OpenAI's `model_not_found` error (404, `invalid_request_error`, message of the form "The model `X` does not exist or you do not have access to it.").
- **FR-011**: A client disconnect during generation, streaming or not, MUST stop all upstream generation for that request (including every call made to serve `n > 1`) within 1 second, by cancelling the in-flight upstream requests; the request is recorded as cancelled.

**Persistence**

- **FR-012**: The system MUST record every generation request that reaches the endpoint logic (i.e. passed schema validation), whether successful, failed, or cancelled, including: identifier, timestamp, model, status, streaming or not, key request parameters, input messages, output content, finish reason, input/output/total token counts, total request duration, time to first token (for streaming), model load duration, and generation duration.
- **FR-013**: Failed requests MUST be recorded with their error type and message.
- **FR-014**: Recorded data MUST survive server restarts.
- **FR-015**: Stored content (input and output) and stored metadata MUST be separable such that metadata can be exposed without ever exposing content.

**Playground tab**

- **FR-016**: The web app MUST provide a sidebar from which the user switches between the Playground tab and the Analytics tab.
- **FR-017**: The Playground MUST offer a control for every option of the endpoint, with defaults (the endpoint's own defaults shown as placeholders), and MUST send only the options the user set.
- **FR-018**: The Playground MUST let the user build a multi-message conversation (system, user, assistant roles) and send it. Messages are text only: image attachment is API-only for now and has no Playground control (an exception to FR-017's "every option").
- **FR-019**: The Playground MUST display the model's answer, support streaming on and off, and let the user cancel an in-progress streamed answer.
- **FR-020**: The Playground MUST show a history of requests with each request and its answer, and let the user reopen an entry to see its full details.
- **FR-021**: The Playground MUST show server error messages to the user unchanged.
- **FR-022**: The Playground MUST reach the server only through the same public API an external client uses.

**Analytics tab**

- **FR-023**: The Analytics tab MUST list all recorded requests, newest first, with timestamp, model, status, input tokens, output tokens, total tokens, total duration, time to first token where applicable, model load duration, and generation duration.
- **FR-024**: The Analytics tab MUST NOT display or receive any request or response content.
- **FR-025**: The Analytics tab MUST show aggregate summary figures over the recorded requests (request count, total input and output tokens, average durations, error rate). Error rate is failed requests divided by all requests; cancelled requests are not errors.
- **FR-026**: The Analytics tab MUST handle large histories by loading in pages, and MUST show a clear empty state when there are no requests.
- **FR-027**: The metadata the Analytics tab shows MUST come from a server endpoint reading the stored records, following the project's conventions for additional (non-OpenAI) endpoints.

**Models**

- **FR-028**: The system MUST expose `GET /v1/models` with exactly OpenAI's contract (`ListModelsResponse` of `Model` objects), listing the served models from the database.
- **FR-029**: The Playground MUST offer the served models (from `GET /v1/models`) as a model selector, and MUST NOT allow typing an arbitrary model name.

### Key Entities

- **Chat Completion Request Record**: One entry per call to the endpoint. Holds identity and time, model, outcome status (succeeded, failed, cancelled), streaming flag, the request parameters used, the input messages, the output content and finish reason, token counts (input, output, total), timing (total duration, time to first token, generation duration), and error details when failed.
- **Request Metadata View**: The content-free projection of a record (everything above except input messages and output content), used by the Analytics tab and its summary figures.
- **Playground History Entry**: A user-facing pairing of a request (messages and options) with its answer or error, as seen in the Playground.
- **Model**: A served local model (initially only the Qwen model), stored in the database with its Ollama tag as identifier, creation time and owner; the one source for `GET /v1/models`, request validation, and the Playground selector.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: An unmodified OpenAI SDK client, with only its base URL changed, completes both a non-streaming and a streaming chat request successfully against the server.
- **SC-002**: 100% of the options defined by OpenAI for this endpoint pass schema validation when well-formed, and each is documented as honored, ignored, or rejected as unsupported, with a test asserting the policy table covers every property of the vendored request schema.
- **SC-003**: Responses from the server pass automated validation against OpenAI's published contract for this endpoint, for success and error cases.
- **SC-004**: For streaming requests, the first content appears in the Playground within 2 seconds of sending once the model is loaded, on the target platform (a macOS Apple-silicon machine, see `.claude/CLAUDE.md`).
- **SC-005**: 100% of generation requests that reach the endpoint logic (success, failure, cancelled) appear in the Analytics tab, with token counts matching those returned to the client.
- **SC-006**: No request or response text is ever present in what the Analytics tab receives or displays.
- **SC-007**: A user can send a first message from the Playground and read the answer in under 1 minute from opening the app, after the documented setup (Ollama running, model pulled), with no further configuration.
- **SC-008**: The Analytics tab stays responsive (list visible in under 2 seconds) with at least 10,000 recorded requests.

## Assumptions

- Single local user, no authentication, consistent with the project's current conventions; the Playground and Analytics show all requests regardless of origin.
- The exact model is chosen during planning: the newest Qwen generation in the Ollama library under 10B parameters at that time, confirmed by checking the library rather than assumed. The chosen model (`qwen3.5:9b`, see research.md) accepts images, but this feature supports text and inline (base64) image content only; audio is unsupported.
- Reasoning and verbosity style options are honored only where the chosen model has an equivalent; otherwise they fall under the "accept and ignore" policy of FR-004.
- Only models stored in the database are served; any other model name is rejected exactly as OpenAI rejects an unknown model. The model id is the Ollama tag. `GET /v1/models/{model}` (retrieve) and model deletion are out of scope.
- Playground history lives in the browser for the current session and is not required to persist across reloads; the durable history is the stored request records.
- The Playground history shows only requests made from the Playground; the Analytics tab covers requests from all clients.
- Requests rejected by schema validation before reaching the endpoint logic (malformed body, wrong types) are not recorded: only generation (LLM usage) is recorded, not endpoint hits. Every request that reaches the endpoint logic is recorded, including unsupported-option and unknown-model rejections and upstream failures.
- Analytics is read-only: no editing or deleting of records, and no charts are required beyond a list and summary figures.
- Request content is stored locally (required by the feature) but is deliberately never exposed through the Analytics path.
- The batch API, the legacy completions endpoint, embeddings, and other endpoints are out of scope for this feature. This includes OpenAI's stored-completion endpoints on the same path (`GET /v1/chat/completions`, `GET|POST|DELETE /v1/chat/completions/{id}` and its messages), which are not implemented and return the standard unknown-route/method error.
- A structured-output request whose generated text does not conform to the requested JSON/schema is returned as generated (no server-side validation or retry). Empty or very long message content is passed through; only the context limit applies.
- Constitution compliance: local-only inference through Ollama (Principle II) is honored; usage and request state live in SQLite and feed the UI via `/v1` endpoints (Principle V); live-request priority (Principle IV) is trivially satisfied as no batch workload exists yet.
